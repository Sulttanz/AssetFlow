Executive summary

Historical snapshot: This HTML report was written on 22-10-2026 and predates later schema and routing changes. Use docs/architecture-blueprint.md for the current route tree, 93-table schema inventory, module and persona gates, report sources, and SLA behavior.

The repository contains a broad, integrated enterprise IT operations product: employee and access lifecycle controls, ITSM workflows, a manual CMDB, asset and software-seat tracking, procurement and maintenance, vendor contracts, knowledge articles, service catalog approvals, handover receipts, and an executive dashboard. The architecture is a conventional React/Vite client, Express API, Drizzle data layer, and PostgreSQL database.

What is strongest: the main workflows are represented by distinct relational records; ticket, approval, change, access, and handover events have audit/activity paths; and database migrations are tracked separately for on-prem deployment.

What needs attention before calling this enterprise-complete: project management is only registered as a disabled upcoming module; automated SLA escalation currently targets the generic ticket table rather than all newer incident/request records; cloud cost data is stored but not reconciled from provider billing feeds; audit records lack database-level tamper-evidence; and the native date-input UI still depends on browser locale.

Interpretation: this is a code/schema audit, not a production-data review, penetration test, formal control assessment, or certification opinion. “Supports alignment” below does not mean ISO 27001, NCA, or SAMA compliance has been independently established.

Core technology and deployment architecture

Application stack

  • Frontend: React 18, TypeScript, Vite, Wouter routing, TanStack Query, and shared Tailwind/shadcn-style UI components.
  • Backend: Node.js and Express 4, with API routes grouped mainly in server/routes.ts and focused modules for auth, knowledge governance, service catalog, vendor contracts, and handovers.
  • Data access: Drizzle ORM and shared TypeScript table/validation definitions in shared/schema.ts.
  • Database: PostgreSQL. Runtime configuration uses workspace secrets such as NEON_DATABASE_URL; secret values are intentionally not included.
  • Authentication: server-side session flow, PostgreSQL session table/store, password verification, and optional 2FA setup/verification endpoints.

Request and data flow

Browser UI → authenticated Express /api routes → persona/module/permission checks → storage/Drizzle → PostgreSQL.

Vite serves the development client. Production is built with npm run build; npm start runs the bundled server and built client. The configured development workflow is npm run dev.

Uploads are represented by metadata and paths in database rows; the inspected route code uses server-side filesystem upload paths rather than a discovered managed object-storage adapter.

Schema and migration path

  • Drizzle schema is the shared application contract; the workspace exposes npm run db:push for schema synchronization.
  • On-prem SQL changes are separate from Drizzle-managed schema changes and are applied by server/startup-migrations.ts.
  • The on-prem runner records applied migrations in the onprem_deploy ledger schema and checks already-applied entries. The current on-prem directory contains 19 SQL migration files.
  • Recent additions include inventory, employee/access governance, CMDB, change impact links, knowledge governance, service catalog, vendor contracts, and asset handovers.

Operational background work

  • Access expiry: an immediate sweep and a five-minute interval update active access grants whose end date has passed, then add an audit row within the same database transaction.
  • SLA enforcement: starts 30 seconds after server boot and runs every five minutes. It escalates overdue open generic tickets to critical and adds an internal system comment.
  • CAB live updates: event streams and expiring database leases support active approval views; process-local event fan-out is reconciled through polling. Multi-instance deployments should not assume process memory is a shared event bus.

Key entities and high-value fields

Identity and access

employees stores employee number, name, email, status, offboarding date/reason, department, manager, position, location, phone, start date, and salary. employee_access_rights stores catalog/access type, privilege, account name, required business justification, grant/expiry dates, status, and revocation data. employee_offboarding_clearances records asset return, credential/VPN revocation, and license reallocation sign-off or waiver notes.

employee_access_rights.employee_id restricts employee deletion; the employee record does not carry a direct users.id FK. Ticket and portal identity resolve through authenticated user records and matching employee email in several read paths.

Assets and software/cloud FinOps

The broad assets table includes tag, serial/model/manufacturer, asset type/category/status, owner/custodian, location/department/vendor, acquisition/warranty/contract dates, security/compliance posture, financial valuation/depreciation, maintenance, software license type/key/quantity/used seats/expiry, and cloud provider/tenant/billing cycle/recurring cost/auto-renewal.

software_license_allocations links a software asset pool to employees and allocation/release timestamps. Assets hold cloud and license cost metadata; no provider-billing ingestion ledger is present in this schema.

CMDB and documents

cmdb_applications includes category, vendor, business/technical owners, hosting type, criticality, and status. servers includes hostname, IP, OS, environment, specs, location, and status. application_server_links is the many-to-many mapping. configuration_documents references an application or server and stores type/version, original/file names, content type/size/path, uploader, and upload time.

A database check enforces exactly one document parent. Documents are version-labelled, but version history is not a separate immutable content archive.

Service desk and change

incidents tracks creator/requester, assignee/group, severity/priority/status, asset, SLA policy, response/resolve due dates, timestamps, resolution code, and notes. service_requests tracks requester and creator separately, service/catalog item, approval/fulfilment state, dynamic field values/schema snapshot, target/due dates, fulfilled asset, and completion/closure note.

changes stores plans, risk/impact, schedule/actual timestamps, CAB requirement, submit/approval times, requester/assignee, department, and project. Separate tables hold approval history, deployment stages/evidence, PIR, risk links, and affected CI links.

Catalog, knowledge, and risk

service_catalog_items includes JSON custom-field schema, SLA hours, approval role, and active state; submitted requests snapshot the schema. service_requests_approvals retains approver, decision, note, and time. kb_articles includes publication visibility, ownership, review date, and version; kb_article_versions stores snapshots and change notes. kb_ticket_links retains the linked article version.

risk_register stores likelihood, impact, score, mitigation, contingency, owner, due date, residual score, status, and acceptance reason; risks can link to changes without being limited to them.

Finance, vendor, warehouse

vendors contains contacts, category, risk/compliance details, support data, and vendor status. vendor_contracts holds contract/SLA dates, notice days, value/currency, tier, and status; bridge tables link contracts to assets, POs, and servers.

Purchase orders have line items and receipt records. Budgets store fiscal year, department/location, amount, spent amount, category, and notes. Warehouses and consumables have movement and dispatch history. The schema has no direct PO-to-budget FK or allocation junction.

Relational integrity and deletion behavior

  • History-preserving restrictions: employee entitlements and clearances, handovers, service catalog items referenced by requests, approved request records, and contract links restrict destructive deletes where history is material.
  • Parent-owned cleanup: incident/request activities, change approvals/stages/PIR, application-server links, risk links, and ticket/KB associations cascade when their owning record is deleted.
  • Optional actor references: many user/owner FKs use SET NULL so an account removal does not erase the business record.
  • Checks: constraints cover offboarding clearance values, handover type/condition/accessory JSON/acknowledgment coherence, vendor contract date/cost/currency/status, one-parent configuration documents and change CI links, catalog SLA and approval role, and approval decision notes.
  • Concurrency: business workflows use transactions and some domain-specific conflict responses; a single universal version/ETag strategy across all CRUD entities was not evident.

Record scoping observed in the ITSM API

Current collection-query behavior: GET /api/incidents returns all rows to elevated helpdesk/manager permissions and otherwise filters to creator or requester. GET /api/service-requests filters non-elevated users to requester-owned records, with approval visibility exceptions. The collection filters do not include a non-elevated assignee match, despite the broader “created or assigned” scope requested in earlier product requirements. Confirm whether that is intentional before expanding staff visibility.

End-to-end workflows represented in code

  1. Self-service request: employee selects a catalog item, enters schema-driven values, and submits a service request. The submitted schema is snapshotted. Approval-required requests wait for an authorized decision; approved requests enter agent fulfilment, and consumable fulfilment records stock movement before completion.
  2. Incident response: an employee or staff member creates an incident, optionally on behalf of a requester; assignment, status, activity history, asset association, SLA dates, resolution notes, and incident-to-change conversion are represented.
  3. Change control: a change is submitted, routed through CAB decisions and environment stages, linked to affected applications/servers and risks, completed with implementation timestamps, and followed by PIR capture.
  4. Employee offboarding: review flags assigned assets, access grants, and software seats; formal clearance records cover return, credential/VPN revocation, and license reallocation. Finalization requires completion or an explicitly noted waiver.
  5. Asset custody: staff issue, return, or replace an asset through a handover receipt. The action links employee, asset, assignment, issuing user, condition, accessories, and acknowledgment/signature data; employees can acknowledge their receipt.
  6. Knowledge feedback: agents search and attach a versioned article to an incident or service request; the association preserves article version for later reference.
  7. Procurement to stock: PO lines and receipts support assets or consumables; consumable movement and dispatch logs retain warehouse, actor, requester, quantity, and service-request references.

5. Security, governance, and compliance posture

Persona and permission model

The application recognizes normalized personas end_user, it_agent, cab_member, it_manager, and auditor, alongside admin and legacy role aliases. Authorization composes persona page/API rules with database-backed permissions and module gates. Multiple persona assignments are additive; admin/system-admin permissions bypass persona restrictions.

PersonaObserved workspace boundaryImportant qualification
End userPortal, service catalog, personal assets, knowledge, and personal incident/request routes; own handover receipts can be acknowledged.Incident collection is creator/requester scoped; service request collection is requester scoped. Assigned-handler matching is not included for non-elevated collection calls.

Controls visible in the code

  • Session authentication, optional 2FA endpoints, role/permission tables, module-level enable/disable, route permission checks, and persona-aware navigation/API checks.
  • Offboarding clearance types and statuses are constrained; access decisions store actor/reason/time information. Expired access is changed and audited in a transaction.
  • Ticket/incident/service-request updates enforce workflow rules such as approval before completion, stock fulfilment before closure, and closure notes in controlled actions. Domain-specific conflicts return HTTP 409 where state must be refreshed or a transition is invalid.
  • Case-insensitive dropdown duplicate cleanup/uniqueness handling exists; the lookup API returns conflict responses for duplicate values.
  • Human-readable date utilities standardize displayed dates to DD-MM-YYYY and date-times to DD-MM-YYYY HH:mm; persistence remains database/ISO-oriented.
  • Audit log views are read-only through the exposed API. Core access, handover, knowledge, service-catalog, and vendor mutation paths include audit writes; transaction placement varies by workflow.
Date-input caveat: formatted text uses the shared date utility, but native <input type="date"> controls remain in risk and change forms. Their placeholder and visual date order are browser/OS locale-dependent, so the UI cannot promise DD-MM-YYYY display for every native picker.
Audit immutability caveat: application routes do not expose a normal audit-log update/delete flow, but the schema and migration inventory do not establish a database-enforced append-only policy, tamper-evident hash chain, WORM retention, or segregated audit administrator boundary. “Immutable” should therefore be treated as application-level intent, not cryptographic or storage-level proof.

ISO 27001, NCA, and SAMA alignment

Asset classification, security posture, compliance metadata, vendor risk fields, access reviews, approvals, activity history, and audit logs provide useful control evidence inputs. However, the code does not by itself prove alignment or certification against ISO 27001, NCA ECC/CCC, or SAMA CSF. A defensible compliance claim still requires a mapped control register, evidence retention/ownership, formal risk acceptance, operational procedures, independent testing, and the applicable organization-specific scope.

No complete SAML/OIDC/SCIM identity federation or provider billing synchronization was evident in the inspected auth and integration paths. Confirm external integrations separately before deployment decisions.

Position relative to common enterprise suites

Capabilities already comparable at the workflow level

  • Incident/request intake, assignment, activity, closure, approvals, service catalog forms, and knowledge linking.
  • Change/CAB controls, risk scoring, CI impact mapping, staged deployment records, and PIR.
  • Employee access reviews/offboarding, asset custody receipts, software allocations, inventory, maintenance, purchase orders, contracts, and reports.

What still separates a broad platform from a mature Tier-1 deployment

  • Automated discovery/reconciliation and service topology; provider-backed licensing/cost feeds.
  • Federated identity lifecycle, cross-system orchestration, and production-grade outbound notification delivery.
  • Provable audit immutability, formal control mappings, resilient file storage, and operational recovery evidence.
  • Unified SLA semantics, workload scoping, configurable workflow automation, and dedicated project management.
