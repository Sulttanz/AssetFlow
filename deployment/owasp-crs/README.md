# On-premises OWASP CRS ingress examples

These files are **not loaded by the Node application or the Replit edge**. They are starting configurations for an administrator-managed HTTPS ingress with a supported ModSecurity v3 Nginx connector and a maintained OWASP CRS release. See the official [CRS installation guide](https://coreruleset.org/docs/1-getting-started/1-1-crs-installation/) and the connector's version compatibility requirements.

For the future container-based deployment, see [`../onprem/README.md`](../onprem/README.md). It uses the official image's generated rules/configuration paths rather than these host-package paths.

1. Install the engine, Nginx connector, baseline ModSecurity configuration, and official CRS release on the ingress host.
2. Adjust the `Include` paths in `modsecurity-crs.conf` to match the installed packages. Copy it to `/etc/nginx/modsecurity/owasp-crs.conf`. Copy the empty `app-crs-exclusions.conf` to `/etc/modsecurity/app-crs-exclusions.conf`. Ensure the audit log directory exists with restricted service-account write access.
3. Add the contents of `nginx-location.conf` to the existing TLS-enabled server block. Preserve its certificate configuration. Bind the Node application to `HOST=127.0.0.1` and restrict network access to the Node port so clients cannot bypass the WAF.
4. Validate the complete Nginx configuration with `nginx -t`. In staging, first observe legitimate login, ticket text, upload, import, and report-export traffic using detection mode. Review false positives and use narrow, documented exclusions only. The shipped example is explicitly **blocking mode** (`SecRuleEngine On`); promote it only after those staging checks.
5. Verify controlled security probes are rejected by the **edge**, that the actual runtime configuration includes all CRS rule files, and that audit records contain the CRS rule IDs. A successful Express response or application-level origin rejection does not establish CRS enforcement.
6. Use `AHZ` to omit request/response headers and bodies, but do not assume this removes sensitive matched input from CRS rule messages. Restrict raw audit/error files and redact matched-data fields before centralized ingestion. If the ingress access log captures IP, timestamp, method/path, and user agent, exclude query strings and sensitive headers and use structured escaping. Apply retention and access controls. Forward edge events through an approved authenticated log pipeline if they need to appear in System Audit Logs: requests blocked at the ingress never reach Express, so application middleware cannot capture them.

The request-body ceilings allow the application's 20 MB attachments and 10 MB spreadsheet report JSON bodies. They do not replace its smaller endpoint-specific limits. The Express session trusts one proxy hop; overwrite forwarding headers at that trusted ingress, and configure real-client-IP handling explicitly if additional proxies precede it.
